# PricePilot v1.3 --- UI/UX Design Specification

**Status:** Approved direction; implementation details subject to
read-only repository audit\
**Design identity:** Midnight Intelligence\
**Themes:** Dark and light\
**Density:** Balanced\
**Responsive strategy:** Mobile-first, then desktop refinement\
**Motion:** Preserve the existing ambient background; selectively refine
other motion

## 1. Design objective

PricePilot should feel like a polished shopping-intelligence product:
distinctive, trustworthy, and practical. Product information and
purchasing decisions should dominate. Decorative effects should support
the product rather than compete with it.

This specification describes intended behavior; it does not assert that
the current code already supports it. Before implementation, inspect
routes, shared components, CSS conventions, theme behavior, and tests.

## 2. Visual identity and palette

Use a dark graphite foundation, layered neutral surfaces, restrained
violet accents, clear typography, and deliberate spacing. Keep the
product atmospheric without turning every surface into a glow, gradient,
or glass panel.

Proposed palette starting points; validate contrast and compatibility
before implementation:

  Semantic role     Dark theme   Light theme
  ----------------- ------------ -------------
  Page background   `#111116`    `#F6F6FA`
  Primary surface   `#202029`    `#FFFFFF`
  Primary text      `#F6F5FA`    `#22222D`
  Secondary text    `#C7C5D2`    `#555565`
  Border            `#393946`    `#DCDCE5`
  Primary accent    `#9585FF`    `#6353D9`
  Accent surface    `#282733`    `#ECE9FF`

These are proposals, not an instruction to replace existing values
blindly. Validate contrast for text and controls. Success, warning,
error, and informational states must be distinguishable in both themes
and must not rely on color alone.

## 3. Shared design system

### Typography

-   Use one consistent sans-serif family unless the repository already
    has a deliberate compatible choice.
-   Define roles for page title, section heading, body, metadata, label,
    and price.
-   Use price size and weight to establish hierarchy without making
    every number oversized.
-   Keep source and freshness metadata readable.

### Spacing and geometry

-   Use a consistent 4px-based spacing scale.
-   Define a small set of radii for controls, cards, and overlays.
-   Keep content width and alignment consistent across related pages.
-   Use borders to distinguish surfaces and shadows sparingly.
-   Prefer consistent padding and alignment over arbitrary per-card
    styling.

### Components

Define semantic variants for primary/secondary/tertiary/destructive
buttons; inputs and filters; product and offer cards; status labels;
comparison rows; dialogs, drawers, menus, tooltips, notifications; and
loading, empty, error, and unavailable states.

Reuse existing components where practical. Do not create a parallel
component system if the current architecture can be extended cleanly.

### Theme behavior

-   Provide a user-controlled dark/light toggle.
-   Persist the user's choice using existing application conventions
    where possible.
-   Choose a deliberate default if no preference exists.
-   Apply theme semantics to pages, menus, dialogs, dropdowns, charts,
    forms, tooltips, and status states.
-   Avoid flashes of the wrong theme where practical.
-   Verify contrast and focus visibility in both themes.

### Accessibility

-   Interactive controls have accessible names.
-   Keyboard focus is visible and not obscured by sticky UI.
-   Hover is never the only way to expose an action.
-   Respect reduced-motion preferences for nonessential movement.
-   Use practical mobile touch targets.
-   Provide accessible summaries for important chart information.

## 4. Global application shell

-   Preserve consistent branding and route navigation.
-   Keep primary destinations discoverable and secondary destinations
    compact.
-   Place the theme toggle where it is easy to find.
-   Keep currency selection accessible where prices are displayed or
    configured.
-   Preserve guest access to public discovery; request sign-in only for
    account-dependent capabilities.
-   Prevent sticky headers from colliding with content, drawers,
    dialogs, and focused elements.
-   On mobile, secondary destinations may move into a menu, but core
    shopping actions must remain discoverable.

Final labels and placement must map to actual routes and capabilities
found in the repository. Do not invent duplicate destinations.

## 5. Page specifications

### 5.1 Landing page

**Goal:** Explain the value and get users into discovery quickly. -
Concise headline and supporting copy. - Prominent search. - Primary
shopping actions before secondary analytics/account features. -
Consistent featured-product cards. - Preserve the existing ambient
background and intended motion. - Avoid an oversized hero that pushes
useful content below the fold.

**Acceptance** - First-time visitors understand the purpose and can
begin searching immediately. - Search and featured-product actions work
by keyboard and touch. - First viewport remains focused on common mobile
and desktop sizes. - Empty/unavailable data does not produce fake
products or decorative dead ends.

### 5.2 Search and discovery

**Goal:** Help users find the right product efficiently. - Keep the
query and result context visible. - Prioritize image, name, meaningful
model/variant, and price when available. - Make sorting easy to discover
and show the active order. - Desktop may use a filter sidebar. - Mobile
filters use a drawer/sheet with clear Apply, Reset, and close
behavior. - Preserve current pagination/loading behavior unless an
observed issue justifies change.

**Acceptance** - Loading, results, no-results, and error states are
distinct. - Applying filters does not silently discard the query. -
Mobile filters work without horizontal overflow. - Card targets and
secondary actions are clear and nonconflicting. - Existing
search/discovery tests pass.

### 5.3 Product detail

**Goal:** Support an informed product decision. Recommended order: 1.
Product image, name, brand/model, and variant. 2. Current price and best
available offer only when supported by data. 3. Primary actions: compare
offers, manage watchlist, visit seller. 4. Price history and context. 5.
Alternatives, recommendations, and other intelligence.

Desktop may use a two-column summary; mobile stacks identity, price, and
actions naturally. Do not show fabricated trends when history is
missing.

**Acceptance** - Product identity, variant, and currency are
unambiguous. - External offer claims have source and observation
information when available. - Missing history is explained rather than
shown as a misleading empty chart. - Primary and secondary actions have
clear hierarchy. - Watchlist, comparison, currency, and assistant
handoffs retain existing behavior.

### 5.4 Seller cards and marketplace offers

**Goal:** Make offers comparable, not simply make the lowest number look
best.

Show when available: seller/marketplace identity; listed price and
currency; known shipping/additional costs; total comparable price only
when required fields and assumptions are known; source URL and
last-checked time; and explicit
live/cached/stale/demo/user-submitted/unavailable status as applicable.

Use restrained best-value styling. Do not label an offer "best" solely
because its displayed price is lowest if cost completeness, variant
identity, or data quality makes that conclusion unreliable.

**Acceptance** - Materially different variants are not silently treated
as identical. - Missing shipping data is not interpreted as zero. -
Cached/stale/demo/user-submitted data cannot be confused with fresh
verified live data. - Outbound links lead to the corresponding source. -
Currency and seller-card regression tests pass.

### 5.5 Product comparison

-   Align products and key specifications for scanning.
-   Put price and important differences near the top.
-   Emphasize actual differences.
-   Represent missing specifications consistently; missing does not mean
    equal.
-   On mobile, use a compact summary and a usable way to inspect
    specifications instead of forcing a wide desktop table into a narrow
    viewport.

**Acceptance** - Product identity and variant remain visible. - Missing
values are explicit. - Currency formatting is consistent. - Existing
add/remove/replace behavior works. - No unintended page-wide horizontal
overflow at mobile widths.

### 5.6 Dashboard

-   Prioritize useful summaries such as watchlist movement, meaningful
    price changes, and recent activity when available.
-   Keep metrics subordinate to useful actions.
-   Avoid duplicate metrics and a wall of cards.
-   Explain empty or insufficient-data states.

**Acceptance** - Summaries use actual application data. -
Empty/loading/error states provide a useful next step. - Existing
navigation and dashboard behavior remain functional.

### 5.7 AI shopping assistant

-   Use a readable conversation layout.
-   Render product suggestions as structured, scannable content.
-   Include source links and relevant price/context when available.
-   Keep follow-up actions contextual and limited.
-   Distinguish verified application data from generated explanations.

**Acceptance** - Recommendations link to real application products or
offers. - Generated claims are not presented as verified stock,
retailer, or price facts. - AI-unavailable behavior retains
deterministic fallback where supported. - Assistant, currency, and
product-handoff tests pass.

### 5.8 Analytics and price history

-   Make chart title, time range, currency, and key values clear.
-   Use restrained grid lines and distinguish series accessibly.
-   Provide text summaries for important chart information.
-   Avoid unnecessary chart animation.
-   Explain sparse or missing history.

**Acceptance** - Charts reflect available data and selected time
range. - Currency conversion does not silently change the meaning of
historical data. - Sparse/missing history is explicit. - Charts remain
legible in both themes and on mobile.

### 5.9 Watchlist and notifications

-   Use compact product rows with identity, current/tracked price where
    available, and alert status.
-   Keep alert configuration and removal discoverable.
-   Notifications explain what changed and link to the product.
-   Distinguish read/unread states without relying only on color.

**Acceptance** - Alert status, current price, and product identity are
not conflated. - Empty watchlists lead back to discovery. - Existing
watchlist and notification actions continue to work.

### 5.10 Authentication, preferences, and management

These pages receive shared consistency improvements after core journeys
stabilize, not a blanket redesign. - Consistent labels, form spacing,
validation, focus, and error messages. - Group preferences logically and
make theme/currency controls easy to find. - Keep management tables
readable and destructive actions distinct. - Preserve authorization and
protected-route behavior.

**Acceptance** - Forms work by keyboard and expose accessible labels. -
Validation is close to the relevant field and not color-only. - Theme
and currency settings behave consistently. - Authentication and
authorization behavior is unchanged.

## 6. Motion and ambient background

-   The current committed ambient background is explicitly out of scope
    for modification during the initial UI pass.
-   Do not remove, replace, or rewrite it as a cleanup shortcut.
-   Refine other animation only when it improves state communication or
    feedback.
-   Use short, consistent transitions.
-   Avoid constant motion that competes with product information.
-   Do not add cursor-following effects, glowing borders, or animated
    gradients without a user-centered purpose.
-   Respect reduced-motion preferences for nonessential movement.

## 7. Mobile-first rules

-   Design narrow layouts first, then expand for tablet and desktop.
-   Avoid horizontal overflow in the page shell.
-   Use full-width primary actions when useful on mobile.
-   Make filters, menus, dialogs, and selectors touch-friendly and
    dismissible.
-   Keep prices, source, and freshness information readable.
-   Ensure sticky content does not cover headings or focused elements.
-   Verify at least one narrow mobile width and one common desktop width
    in both themes.

## 8. Implementation order

1.  Read-only audit of routes, shared components, tokens, theme
    handling, tests, and ambient background.
2.  Shared design tokens and theme toggle.
3.  Shared controls and surfaces.
4.  Landing/search/product/offer/comparison journeys.
5.  Dashboard, assistant, analytics, watchlist, and notifications.
6.  Authentication, preferences, and management consistency.
7.  Browser verification, accessibility checks, regression tests, and
    visual fixes.

The audit must determine which components can be reused and whether a
new abstraction is justified. Do not implement the design system based
on assumptions alone.

## 9. Cross-cutting definition of done

-   [ ] Dark and light themes work across core screens and overlays.
-   [ ] Theme choice persists according to agreed application behavior.
-   [ ] Core screens work at narrow mobile and common desktop sizes.
-   [ ] Shared typography, spacing, controls, surfaces, borders, and
    focus states are consistent.
-   [ ] Ambient background implementation is unchanged.
-   [ ] Reduced-motion behavior is verified.
-   [ ] Keyboard navigation and visible focus are verified.
-   [ ] Loading, empty, error, and unavailable states are deliberate.
-   [ ] Price/source/freshness claims remain truthful.
-   [ ] Browser inspection verifies both themes on mobile and desktop.
-   [ ] Frontend build and relevant tests pass.
-   [ ] Relevant backend/service tests pass if those parts are touched.
-   [ ] `git diff --check` passes.
-   [ ] Existing v1.2 flows remain functional.

## 10. Design constraints

Do not remove/replace the ambient background, overuse
gradients/glass/glow/animation, redesign every page before shared
foundations stabilize, invent data to fill visual space, duplicate the
architecture with a parallel component system, or pull v1.4 features
into v1.3.

## 11. Approval boundary

This document records the approved direction and intended behavior.
Exact token values, component reuse, route mapping, theme persistence,
and implementation boundaries must be checked against the current
repository before code changes begin. No implementation should start
until the read-only audit confirms compatibility.
