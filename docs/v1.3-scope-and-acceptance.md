# PricePilot v1.3 --- Scope and Acceptance Criteria

**Status:** Proposed implementation contract\
**Release:** v1.3 --- Marketplace Intelligence\
**Branch:** `develop`\
**Design direction:** Midnight Intelligence\
**Planning window:** 7 days, beginning 11 October 2026

## 1. Purpose

v1.3 should improve marketplace offer comparison and the consistency of
the core shopping experience while protecting PricePilot's ML
engineering milestones. The release has two workstreams: a bounded UI/UX
redesign and a focused marketplace-offer capability, subject to an
authorized and feasible data source.

## 2. Locked decisions

-   Visual identity: **Midnight Intelligence**.
-   Themes: dark and light, with a user-controlled toggle.
-   Information density: balanced.
-   Motion: preserve the existing ambient background; selectively refine
    other motion.
-   Redesign scope: shared foundations and core shopping journeys first.
-   Responsive strategy: mobile-first, then desktop refinement.
-   Work on the existing long-lived `develop` branch; no feature
    branches.
-   Target at least two meaningful commits per day; never create trivial
    commits merely to meet the count.
-   Preserve existing v1.2 behavior.
-   Do not pull v1.4 features into this release.

## 3. In scope

### UI/UX

-   Shared semantic tokens for color, typography, spacing, borders,
    radii, and focus states.
-   Dark/light themes across shared components, pages, overlays, forms,
    charts, and menus.
-   Consistent shared controls and surfaces, reusing the existing
    architecture where practical.
-   Responsive refinement of landing, search, product detail,
    seller-offer, and comparison journeys.
-   Deliberate loading, empty, error, unavailable, and success states.
-   Intentional motion and reduced-motion support.
-   Targeted consistency improvements to dashboard, assistant,
    analytics, watchlist, notifications, authentication, preferences,
    and management pages after core journeys stabilize.
-   Browser/visual verification at mobile and desktop sizes in both
    themes.

### Marketplace intelligence

-   A normalized offer representation separate from the canonical
    product catalog.
-   Offer comparison with source attribution and observation time when
    available.
-   Conservative product and variant matching.
-   A time-boxed attempt to integrate one authorized data provider.
-   Clear live, cached, stale, demo, user-submitted, and unavailable
    states as applicable.
-   Proportionate caching/freshness behavior and graceful handling of
    provider failures.
-   A documented fallback if no suitable authorized provider is feasible
    within the time box.

## 4. Out of scope

-   Changing, removing, or replacing the ambient background.
-   Requiring four live marketplace integrations.
-   Unauthorized scraping or bypassing provider access controls or
    terms.
-   Presenting fixture, demo, cached, or user-submitted prices as
    verified live prices.
-   Complex multi-provider orchestration or a general-purpose scraping
    framework.
-   IndexedDB/offline marketplace search unless justified by a
    demonstrated need.
-   Autonomous checkout or purchase execution.
-   Predictive-shopping features reserved for v1.4.
-   Rewriting every page regardless of need.
-   Unnecessary infrastructure, migrations, or dependencies.
-   Displacing the ML evaluation, reproducibility, and serving
    milestones.

## 5. Marketplace data integrity contract

-   Retain source/provider identity and source URL when available.
-   Retain the time an offer was observed or checked.
-   Use explicit, understandable data-status labels.
-   Never infer that missing shipping cost is zero.
-   Calculate total comparable price only when required fields and
    assumptions are known.
-   Do not compare materially different variants as if identical.
-   Do not claim retailer coverage or live access until tested.
-   Never commit API credentials or secrets.
-   If provider access is unavailable, document the attempt and use
    clearly labelled demo or user-submitted data only if useful.

## 6. Seven-day plan

### Day 1 --- 11 October: Scope and design contract

-   Commit this scope/acceptance document.
-   Commit the UI design specification.
-   No application code changes.

### Day 2 --- 12 October: Shared UI foundations

-   Refine semantic theme tokens.
-   Standardize shared controls and surfaces.
-   Verify both themes without changing the ambient background.

### Day 3 --- 13 October: Product detail and offers

-   Refine product-detail hierarchy and actions.
-   Refine offer presentation and currency clarity.

### Day 4 --- 14 October: Search and responsive behavior

-   Refine search results, sorting, and filters.
-   Verify mobile filter behavior, focus management, and empty/error
    states.

### Day 5 --- 15 October: Marketplace model

-   Define the normalized offer contract.
-   Implement comparison and conservative matching based on the
    repository architecture.

### Day 6 --- 16 October: Provider feasibility and integration

-   Time-box investigation to one authorized candidate.
-   Integrate only if access and reliability are viable.
-   Otherwise, commit a documented fallback decision and limitations.

### Day 7 --- 17 October: Freshness and regression

-   Add proportionate caching/freshness behavior where justified.
-   Run relevant frontend, backend, and service tests.
-   Fix regressions and document limitations.

Each day targets at least two meaningful commits. If blocked, commit a
useful, reviewable result such as a tested fallback or documented
decision rather than claiming an uncompleted integration.

## 7. Acceptance criteria

### UI/UX

-   [ ] Dark and light themes work across core shopping journeys and
    shared overlays.
-   [ ] Theme choice persists across visits according to the
    application's conventions.
-   [ ] Core screens work at narrow mobile widths and common desktop
    sizes.
-   [ ] Typography, spacing, controls, cards, borders, and focus states
    are consistent.
-   [ ] Ambient background implementation remains unchanged.
-   [ ] Reduced-motion preferences are respected.
-   [ ] Keyboard navigation and visible focus are verified.
-   [ ] Loading, empty, error, and unavailable states are deliberate.
-   [ ] Browser inspection verifies both themes on mobile and desktop.

### Marketplace

-   [ ] Offer data is separate from canonical catalog data.
-   [ ] Source and observation time are represented when available.
-   [ ] Live, cached, stale, demo, and user-submitted states cannot be
    confused.
-   [ ] Uncertain variant matches are handled conservatively.
-   [ ] Missing shipping/fee data is not silently treated as zero.
-   [ ] Provider failures degrade gracefully.
-   [ ] No unauthorized collection is used.
-   [ ] Claimed integrations are tested; limitations are stated when
    they are not integrated.

### Regression and release quality

-   [ ] Frontend production build passes.
-   [ ] Relevant frontend tests pass, including currency, search,
    comparison, assistant, and ambient-background tests.
-   [ ] Backend tests pass when backend code changes.
-   [ ] Python AI/SDK tests pass if those services are touched.
-   [ ] `git diff --check` passes.
-   [ ] No secrets or unrelated files are committed.
-   [ ] Existing v1.2 flows are checked for regressions.
-   [ ] No v1.4 features are included.

## 8. Engineering rules

-   Work on `develop`; do not create feature branches.
-   Inspect existing code before adding or replacing abstractions.
-   Prefer small, reviewable changes and avoid unnecessary dependencies.
-   Run tests after relevant changes.
-   Verify visual changes in a browser; a successful build does not
    prove visual correctness.
-   Keep ML claims proportional to available data and evaluation
    evidence.
-   Do not mark criteria complete until verified.

## 9. Career alignment

v1.3 should demonstrate UI engineering, data modeling, integration
boundaries, failure handling, provenance, testing, and scope discipline.
It must not displace PricePilot's core ML evidence: reproducible data
assumptions, baseline models, evaluation protocol, error analysis, and
inference/serving.

## 10. Definition of success

The core shopping journey is coherent and responsive in both themes,
offers are represented honestly and compared conservatively,
external-data failures are handled deliberately, and v1.2 remains
stable. A documented provider-access limitation is preferable to an
unverified or unauthorized integration.
